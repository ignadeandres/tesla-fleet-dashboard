# Implementation Notes — Vehicle Telemetry Polling

**Feature:** Worker adaptive polling state machine + hard daily Tesla API call budget
**Status:** Implemented and shipped. See `docs/vehicle-telemetry-polling/tech-spec.md` for the full architecture/data/API design — this doc covers what's actually in the code, files touched, and gotchas found while reading it.

## Summary

A standalone `worker` Node process (`worker/src/poller.js`) polls each linked vehicle's Tesla Fleet API state on a 60-second base tick, but the actual per-vehicle cadence is decided by `runStateMachine` (`worker/src/stateMachine.js`) from the vehicle's last known state (`driving: 60s`, `charging: 5m`, `idle: 15m`, `asleep: 10m`), gated by an in-memory `lastPollAt` map so most ticks do zero network/DB work. Every branch that reaches the network (the non-waking "lite" check and the full waking poll) is additionally gated by `checkAndConsumeBudget` (`worker/src/apiBudget.js`), a DB-persisted, restart-proof hard cap (`TESLA_MAX_CALLS_PER_DAY`, default 300) on billed Fleet API calls fleet-wide. On a full poll, the state machine writes one `telemetry_snapshots` row and dispatches to independent trip (`worker/src/handlers/trip.js`) and charging (`worker/src/handlers/charging.js`) handlers that open/update/close `trips`+`trip_points` and `charging_sessions` rows, tracking "currently open" per vehicle in in-memory `Map`s (not DB-persisted). All Tesla HTTP access and unit conversion (mi→km) is centralized in the shared `packages/tesla-client` workspace package, consumed by both `worker` and `backend`.

## Key files and their role

- **`worker/src/poller.js`** — process entrypoint. Builds one `pg.Pool` and one `tesla-client` instance, then `setInterval(tick, 60_000)` + an immediate call on boot. `tick()` queries `vehicles INNER JOIN vehicle_tokens` (only vehicles with a stored OAuth token — the seeded demo vehicle is skipped) and loops **sequentially**, calling `runStateMachine` per vehicle inside a per-vehicle `try/catch` so one bad vehicle (expired token, Tesla 5xx, DB error) doesn't abort the rest of the fleet's tick.
- **`worker/src/stateMachine.js`** (`runStateMachine`) — all per-vehicle decision logic. Reads the last `telemetry_snapshots.state` (defaults `"idle"`), looks it up in `INTERVALS_MS`, and returns immediately if not due. If due, marks `lastPollAt` *before* any network call, consumes budget, calls `getVehicleLite` (non-waking); if asleep, writes a single `"asleep"` snapshot only on the state transition (not every tick) and stops. Otherwise consumes budget a second time, calls `getVehicleState` (the full waking poll), derives `driving`/`charging`/`state`, writes one snapshot row, and unconditionally calls both the trip pair (`handleTripPoint` or `closeTripIfOpen`) and the charging pair (`handleChargingUpdate` or `closeChargingSessionIfOpen`) — the two are independent per-tick, not mutually exclusive.
- **`worker/src/apiBudget.js`** (`checkAndConsumeBudget(db)`) — single choke point for every billed Tesla call. `SELECT calls FROM api_call_budget WHERE day = CURRENT_DATE`; if `>= MAX_CALLS_PER_DAY` returns `false` without writing; otherwise `INSERT ... ON CONFLICT (day) DO UPDATE SET calls = calls + 1` and returns `true`.
- **`worker/src/handlers/snapshot.js`** — one-line re-export of `saveSnapshot` from `tesla-client`; no logic of its own.
- **`worker/src/handlers/trip.js`** — `openTrips: Map<vehicleId, {id, startTime}>`. `handleTripPoint` opens a `trips` row on first call (start lat/lng/battery from current data) and always inserts one `trip_points` row. `closeTripIfOpen` re-reads all points for the trip, sums haversine distance (`totalDistanceKm`, `EARTH_RADIUS_KM = 6371`) once at close time (not incrementally), and updates `end_time`/`end_lat`/`end_lng`/`duration_seconds`/`distance_km`/`end_battery_level`.
- **`worker/src/handlers/charging.js`** — `openSessions: Map<vehicleId, {id}>`. `handleChargingUpdate` opens a `charging_sessions` row on first call, then **overwrites** `end_battery_level` on every subsequent charging tick (not appended). `closeChargingSessionIfOpen` computes `energy_added_kwh` as a flat estimate: `((end - start) / 100) * BATTERY_CAPACITY_KWH` (env, default 75) — not Tesla's own energy-added field.
- **`packages/tesla-client/src/client.js`** — `createTeslaClient(db, teslaConfig)` exposes `getVehicleState` (full poll, explicit `endpoints=charge_state;climate_state;drive_state;vehicle_state;location_data` — `location_data` must be requested explicitly or lat/lng come back empty), `getVehicleLite` (bare non-waking `GET`), and `wakeVehicle` (present, never called from the polling path). Internal `call()` runs `ensureFreshToken` before every request. Also exports `fetchTeslaVehicles`, used only right after OAuth code exchange, not part of the polling path.
- **`packages/tesla-client/src/snapshot.js`** (`saveSnapshot`) — shared by worker's poller and backend's manual-refresh mutation; pulls `vehicle_state`/`charge_state`/`drive_state`/`climate_state` off the raw response, converts odometer/battery_range/speed via `toKm`, inserts one `telemetry_snapshots` row (`raw` JSON stringified in full, defaults to `{}`).
- **`packages/tesla-client/src/units.js`** (`toKm`) — `value * 1.609344`, passes `null`/`undefined` through unchanged. Comment notes this was confirmed against a real vehicle: Tesla returns mi/mph unconditionally regardless of the car's own `gui_distance_units` display setting.
- **`packages/tesla-client/src/oauth.js`** (`ensureFreshToken`) — reads stored token, refreshes if within 5 minutes of `expires_at`; the refresh-token rotation update is keyed by `WHERE refresh_token = $stale`, not `vehicle_id`, because Tesla issues one refresh token per account and rotates it on every use (sibling vehicles under the same account must pick up the new token too). This module is shared, not owned by this feature — see `docs/authentication/implementation-notes.md` for its original writeup.
- **`backend/migrations/002_telemetry.sql` .. `006_api_call_budget.sql`** — schema matches the tech spec exactly, confirmed line-by-line against the code above (`telemetry_snapshots`, `trips`/`trip_points`, `charging_sessions`, `005_trip_battery.sql`'s `start_battery_level`/`end_battery_level` columns on `trips`, `api_call_budget(day PK, calls)`).

## Notable decisions / gotchas for future maintainers

- **`checkAndConsumeBudget` is two sequential queries (`SELECT` then `INSERT ... ON CONFLICT`), not a single atomic statement or transaction.** Fine as-is because `poller.js` processes vehicles strictly sequentially within one process, so there's no concurrent caller today. If the worker is ever scaled to more than one process/replica, this has a TOCTOU race that could let the fleet exceed `MAX_CALLS_PER_DAY` by a small margin — worth an `UPDATE ... RETURNING calls` or `SELECT ... FOR UPDATE` if that ever happens.
- **A single tick can burn up to 2 of the daily budget** (one `checkAndConsumeBudget` call before the lite check, one before the full poll) — this is intentional per the tech spec, but easy to forget when reasoning about how many vehicles `MAX_CALLS_PER_DAY` actually supports per day.
- **`lastPollAt` and both `openTrips`/`openSessions` maps are in-memory and reset on every worker restart.** A restart mid-trip/mid-charge leaves one `trips`/`charging_sessions` row with `end_time` permanently `NULL` and starts a fresh row on the next poll — accepted v1 tradeoff, documented in-code and in the tech spec's ADR, not an oversight.
- **`energy_added_kwh` is a flat capacity estimate**, not read from Tesla's own charging telemetry — `BATTERY_CAPACITY_KWH` env var (default 75, sized for a Model 3 LR) needs to be set correctly per fleet or per-vehicle energy numbers will be wrong for any other battery size; there's no per-vehicle override, just one global env var.
- **`handleChargingUpdate` overwrites `end_battery_level` on every poll while charging**, so a `charging_sessions` row's `end_battery_level` reflects "battery level as of the last poll," not a durable snapshot — if the row is read mid-session (before close), that column is really "current," not "end."
- **The asleep short-circuit only writes a snapshot on the state *transition***, not every tick — confirmed by `stateMachine.test.js`'s "still asleep only records once" test. If you need to know exactly how long a vehicle stayed asleep, that has to be inferred from the gap between the transition-in row and the next full-poll row, not from repeated asleep rows.
- **`toKm`'s mi→km conversion applies unconditionally**, ignoring `gui_settings.gui_distance_units` — a comment in `units.js` explicitly says this was verified against a real car and the display-unit flag does *not* indicate the field's actual unit. If Tesla ever changes this API behavior, this is the one place to check first.

## Verification / test coverage

Ran both relevant suites read-only; all pass:

- `worker`: `npm test` → `node --test $(find src -name '*.test.js')`, **7/7 passing**.
  - `worker/src/apiBudget.test.js` — allows+counts under the cap, blocks (without counting) at the cap. Uses the module's real default (300), since `MAX_CALLS_PER_DAY` is read from `process.env` at import time.
  - `worker/src/stateMachine.test.js` — a never-before-seen vehicle recorded `asleep` polls immediately (not throttled by a stale interval) and opens a trip on the first full poll; a vehicle still asleep records the transition once and never reaches `getVehicleState`; an idle vehicle throttles a second immediate tick to zero lite/full calls.
  - `worker/src/handlers/trip.test.js` — `totalDistanceKm`: 0 for <2 points, and a real Barcelona two-point haversine check (~1.8km, asserted in a 1.5–2.5km band).
- `packages/tesla-client`: `npm test` → **2/2 passing**, both for `units.js`'s `toKm` (mi→km conversion against a real odometer value; null/undefined passthrough).

**Gaps — not covered by any test in the repo:**
- `worker/src/poller.js` — `tick()`'s sequential-with-per-vehicle-try/catch behavior (one vehicle throwing doesn't abort the others) has no test.
- `worker/src/apiBudget.js` — the budget-exhausted path is tested in isolation (`apiBudget.test.js`), but `stateMachine.test.js` never exercises `checkAndConsumeBudget` returning `false` from inside `runStateMachine` (the "daily budget exhausted, skip this vehicle" log/return branch is untested end-to-end).
- `worker/src/handlers/charging.js` — no test file at all; `handleChargingUpdate`/`closeChargingSessionIfOpen` and the `energy_added_kwh` flat-estimate calculation are unverified by any runnable check.
- `worker/src/handlers/trip.js` — `totalDistanceKm` (the pure function) is tested, but `handleTripPoint`/`closeTripIfOpen` (the SQL open/insert/close flow) are only indirectly touched by `stateMachine.test.js`'s assertion that `INSERT INTO trips` fires — the close path (distance/duration/end-battery update) has no direct test.
- `packages/tesla-client/src/client.js` — `createTeslaClient`, `call()`, `getVehicleState`/`getVehicleLite`/`wakeVehicle`, `fetchTeslaVehicles` have no test file (same gap already flagged in `docs/authentication/implementation-notes.md`).
- `packages/tesla-client/src/oauth.js` — `ensureFreshToken`/`exchangeAuthCode`, including the refresh-token rotation query, untested (same pre-existing gap noted in the authentication feature's notes; this feature's worker code depends on it but doesn't add coverage for it).
- `packages/tesla-client/src/snapshot.js` — `saveSnapshot`'s field mapping/unit conversion from raw Tesla response to `telemetry_snapshots` columns has no direct test.
- No test exercises the actual SQL against a real Postgres instance anywhere in this feature — all worker tests use hand-written fake `db.query` objects that pattern-match on SQL substrings, so a migration/query drift (e.g. a renamed column) would only surface at runtime, not in `npm test`.

This is a documentation-only pass — no code, test, or config files were created or modified.
